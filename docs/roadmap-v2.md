## 1. 정의와 원칙

### 한 줄 정의

한 대학 캠퍼스의 길고양이를 지도 기반으로 아카이빙하는 서비스.
"저 고양이 이름 뭐지?"라는 호기심으로 들어와서, "3시간 전 밥 먹음"을 보고 돌봄으로 이어지게 만든다.

### 차별점

급식 로그를 **개인 관리 기록이 아니라 낯선 사람에게 보내는 공개 신호**로 다룬다. 그리고 고정 급식소를 만들지 않는다.

### 원칙 (기능 판단 기준)

1. **"찾아가게" 만들지 말고 "우연히 만났을 때 알아보게" 만든다.**
   - **금지** — 실시간 위치, 위치 기반 푸시/알림, 경로 안내, 실시간 거리 갱신, 특정 개체 추적
   - **허용** — 1시간 지연된 목격 기록을 조회·정렬·필터하는 정적 화면
   - 주변 고양이 보기(§2.7-5)는 허용 쪽이다. **지연을 우회하는 순간 금지 쪽으로 넘어간다**
2. **급식소는 만들지 않는다.** 고정 급식 장소 등록 기능 없음.
3. **급식 기록은 장소가 아니라 고양이 개체에 붙는다.**
4. **사진의 EXIF(GPS 포함)는 무조건 제거한다.**
5. **목격 좌표는 저장 시점에 50m 격자로 반올림한다.** 정밀 좌표는 DB에 존재하지 않는다.
6. **로그인만 하면 모두 고양이 등록할 수 있다.**

> 원칙 1은 2026-07-21에 문구를 좁혔다. 원래 "실시간 위치 알림·경로 안내 없음"이 §3-5(주변 고양이 보기)와 정면 충돌했다. 금지 대상은 **"지금 여기 있다"**이지 **"이 근처에 이런 애들이 산다"**가 아니다.
> 원칙 5는 v1에서 "50~100m 퍼징"이라고만 적혀 있어서 구현이 두 번 뒤집혔다. **랜덤 오프셋이 아니라 결정적 라운딩이다.**

## 2. 확정 사항 — 다시 논의하지 않는다

### 2.1 인증 · 회원가입 (2026-07-19 확정)

**두 갈래를 모두 제공한다.**

| 방식 | 회원가입 | 이후 로그인 |
|---|---|---|
| **이메일** | 가입 폼(이메일 + 비밀번호 + 비밀번호 확인) → 확인 메일 링크 클릭 | 이메일 + 비밀번호 |
| **카카오** | 카카오 인증 (`account_email` 동의항목 포함, §2.8-13) | 카카오 인증 (계속) |

**두 방식 공통:**

- 가입 시 앱 자체 프로필을 새로 만든다
- **집사 이름(닉네임)은 무작위로 자동 생성**한다
- 카카오의 닉네임·프로필 사진은 **저장하지도, 화면에 그리지도 않는다.** 카카오는 오직 인증 통과용
- **대학 이메일 도메인 제한 없음.** 학교별로 나누지 않고 위치 위주로 간다

**Supabase 매핑:**

- 이메일: `signUp({ email, password })` → 확인 메일 링크 클릭 → 이후 `signInWithPassword`
- 카카오: `signInWithOAuth({ provider: 'kakao' })` — Supabase 공식 지원
- 네이버는 채택하지 않는다 (공식 지원 없음, 우회 = 오버엔지니어링)

**메일 발송 인프라** *(2026-08-08 (27) 확정)*

- **커스텀 SMTP를 쓴다 — Resend + 자체 도메인 `gilnyangee.com`.** Supabase 기본 이메일 서비스는 프로젝트 전체 합산 시간당 2통이고, **프로젝트 팀 멤버가 아닌 주소로는 발송 자체를 거부한다.** 즉 기본 SMTP로는 실사용자가 한 명도 가입할 수 없다. 개발 중 본인 주소로만 테스트해서 이 사실이 드러나지 않았다
- **확장자는 `.com`이어야 한다.** `.xyz`·`.shop` 등 저가 확장자는 남용률이 높아 확인 메일이 스팸함으로 간다
- Resend도 **도메인 인증 전에는 계정 본인 주소로만 발송된다.** 커스텀 SMTP를 붙이려면 도메인 구매가 전제조건이다
- 커스텀 SMTP의 기본 한도 = 시간당 신규 사용자 30명. 429가 뜨면 Authentication → Rate Limits에서 숫자를 본다 — **2면 SMTP가 안 붙은 것이고, 30이면 붙은 것이다**
- **코드 변경 없음** — 전부 대시보드·DNS 설정이다
- **OTP 6자리 코드 방식은 2026-08-07 (24) 폐기.** `signInWithOtp` / `verifyOtp` / `updateUser({ password })` 3함수 삭제. 이메일 템플릿은 Supabase 기본값(`{{ .ConfirmationURL }}`)을 그대로 쓴다 — `{{ .Token }}`으로 바꾸지 않는다

**가입 폼은 3필드다 — 이메일 · 비밀번호 · 비밀번호 확인** *(2026-08-07 (24) 확정)*

- **아이디(username)는 만들지 않는다.** Supabase Auth가 username 로그인을 지원하지 않는다. **스코프 초과**
- **이름(실명)은 받지 않는다.** 화면에 뜨는 건 무작위 닉네임이고, 실명은 §2.8-14에 걸린다
- **라벨을 placeholder가 아니라 실제 라벨로 노출한다.**

**가입 대기와 완료 안내** *(2026-08-07 (24) 확정)*

- `signUp` 직후 session은 null이다. 원래 탭은 "메일 확인" 대기 화면에 머무른다
- `emailRedirectTo`는 `window.location.origin + '/?welcome=1'`. **라우트는 만들지 않는다** (§2.10 라우팅 표 불변)
- 링크는 메일 앱 인앱 브라우저에서 열릴 수 있다. **같은 브라우저면** supabase-js가 탭 간 세션을 동기화한다. **다른 브라우저면** 세션을 옮길 방법이 없다
- 그래서 대기 화면에 **"인증 완료했어요" 버튼**을 둔다(A안). 누르면 `signInWithPassword`를 1회 시도한다. **자동 폴링은 하지 않는다**
- 비밀번호는 메모리(React state)에만 둔다

**감수하는 것:**

- 이미 가입된 이메일로 다시 가입해도 "이미 가입됨"을 못 띄운다 — Confirm email이 켜져 있으면 Supabase가 가짜 user 객체를 반환한다
- 미확인 계정에 같은 이메일로 재가입하면 비밀번호가 갱신되지 않는다
- **선행 설정 3건은 코드가 아니라 Supabase 대시보드다** — ① Confirm email ON ② Redirect URLs에 `http://localhost:5173/**`와 Vercel 주소 `/**` ③ 이메일 템플릿 기본값 유지

### 2.2 게스트(비로그인) 접근 범위 (2026-07-19 확정 · 2026-07-21 보강)

**게스트가 볼 수 있는 것은 딱 하나다. 지도에서 마커를 한 번 눌렀을 때 뜨는 카드.**

**카드에 들어가는 것 — 이게 전부:**

- 대표 사진 1장
- 이름
- 최근 밥 언제 먹었는지
- **자유 서술(`description`) 앞 2줄** — 2026-07-22 §2.11로 개정됨

**성별은 카드에 없다.** 성별은 상세 프로필에만 나온다 (§2.7-1).

**게스트가 할 수 없는 것:**

- 상세 프로필 전체 / 도감 리스트 · 검색 · 주변 고양이 보기 / 집사 프로필 · 마이캣
- 모든 쓰기 동작 (밥 주기, 목격 등록, 개체 등록)

> ⚠️ **컬럼 차단은 DB 뷰에서 한다** (§2.8-11). 게스트는 `cats_guest`를 읽는다. 다만 **화면 단위 제한은 여전히 UI 레벨이다.**

**하단 바는 게스트에게도 4탭 전부 보인다** *(2026-07-21 확정, 구 3-16)*

- 나머지 3탭은 **숨기지 않고 잠금 상태로 노출**한다. 누르면 화면 전환 없이 로그인 유도
- 감수 — 게스트 체감이 "막힌 앱"이 된다
- 잠긴 탭을 눌러도 **해당 화면의 데이터를 선제적으로 가져오지 않는다**

> 구조로 보면 **플로팅 카드 = 게스트 / 상세 페이지 = 로그인 게이트.**

### 2.3 위치 저장 방식 (2026-07-17 확정 · 2026-07-19 재확인)

**write-time 라운딩, 격자 50m.**

```javascript
Math.round(v / 0.00045) * 0.00045
```

- 저장 **직전에** 반올림한다. 정밀 좌표는 DB에 들어간 적이 없다
- 마커 UX·지도 바탕은 그대로. PostGIS 불필요. **zones는 사용하지 않는다**
- **노출은 1시간 지연.** 프론트에서 숨기는 게 아니라 **DB가 안 준다.** `cats_guest`/`cats_full` 뷰가 집계 시점에 걸러 `last_lat`/`last_lng`를 NULL로 내린다. **비협상**

`sightings` 컬럼:

| 컬럼 | 비고 |
|---|---|
| `lat` / `lng` | 50m 격자로 반올림된 값 |
| `cat_id` | |
| `created_at` | 지연 계산 기준 |
| `deleted_at` | soft-delete |
| `reporter_id` | RLS "본인만 등록" 검사 |
| `photo_path` | 상세 갤러리 |
| `note` | 목격 메모, 150자 CHECK (2026-08-22) |

> 랜덤 오프셋이 아닌 이유: 랜덤은 기록이 쌓이면 평균으로 원본이 복원된다. 라운딩은 결정적이라 복원할 잔차가 없다.
> 경도 `0.00045°`는 서울 위도에서 약 40m다. 격자가 50×40m 직사각형이 되는 건 감수한다.

### 2.5 데이터 모델 — 6 + `deletion_requests` + `cat_reports` = 실물 8테이블 (§2.16)

`campuses` · `cats` · `sightings` · `feedings` · `profiles` · `bookmarks`

### 2.6 v1 스코프

**만드는 것 (이것만):**

- 지도 + 마커 · 도감(개체 프로필) · 목격 등록 · 급식 원탭 기록 · 인증(§2.1)

- 가입 퀴즈 · 서약서 (§2.7-7)

**안 하는 것:**

- 커뮤니티 / 게시판 · AI 고양이 자동 인식 · 실종 매칭 · 팔로우/좋아요/피드 · 앱스토어 배포

**확정된 권한 규칙:**

- 급식 기록은 지연하지 않는다 (위치 정보가 없고, "N시간째 기록 없음 → 내가 챙기자"가 핵심 루프라서)
- **과급식 방지 — 같은 `kind`의 최근 기록이 2시간 이내면 한 번 되묻는다** *(2026-08-06 (22))*. `water`는 제외. **차단이 아니라 확인이다**
- **고양이 신규 등록은 로그인한 사용자 누구나** (§2.8-12)

### 2.7 2026-07-21 확정 — §3-1 ~ §3-7 이관

1. **게스트 카드 필드 = 대표사진 · 이름 · 최근 밥 · 자유 서술 2줄.** 성별 제외 *(3-1)*
2. **"특이사항"과 "건강상태"를 구분하지 않는다** *(3-2)*
3. **건강상태 필드는 v1에 만들지 않는다** *(3-3)*
4. **`profiles.campus_id`는 v1에서 채우지 않는다(NULL).** 컬럼은 nullable로 유지하고 삭제하지 않는다 *(3-4)*
5. **주변 고양이 보기 = v1 포함.** 1시간 지연된 목격만 사용, 길안내·알림·실시간 갱신 금지 *(3-5)*
6. **마이캣 · 집사 프로필 · 급식 카운터 = v1 포함.** 팔로우/좋아요/피드는 v2 *(3-6)*
7. **가입 퀴즈 · 서약서 = v1 포함.** 완료 플래그는 `profiles.onboarded_at` *(3-7)*
8. **사진 0장 기본 일러스트는 폐기한다** *(2026-07-23)* — 대표 사진이 필수라 사진 0장 상태가 발생하지 않는다. **일러스트는 식별 도구가 아니다** — 캠퍼스에 치즈가 3마리면 구분에 실패한다
9. **카카오 프로필 미저장 유지**

### 2.8 2026-07-21 확정 — §3-11 ~ §3-15

**11. 게스트 제한은 DB 뷰로 한다.**

anon은 `cats` 테이블을 직접 읽지 않는다.

- 게스트 → `cats_guest` (대표사진·이름·최근밥·`description`·`color`·좌표)
- 로그인 → `cats_full` (전체)
- 두 뷰 모두 `sightings` 집계로 `last_lat`/`last_lng`를 만들고 1시간 지연을 적용한다
- 대가 — `cats`에 컬럼이 늘면 뷰 두 개를 같이 고쳐야 한다
- **검증 완료 (2026-07-21)** — `cats_full`에 지연이 없어 로그인만 하면 실시간 좌표가 나가던 것을 고쳤다
- **두 뷰는 `security_invoker`가 꺼져 있다** (`reloptions` = null). 뷰는 소유자 권한으로 돌며 **기저 테이블 RLS를 통과한다**

### 2.12 2026-08-08 확정 — 마이캣 화면

**마이캣은 "내가 소유한 고양이"가 아니라 나와 엮인 개체를 모으는 화면이다.**

- **내가 등록함** — `cats_full.created_by = auth.uid()`
- **밥 준 적 있음** — `feedings.giver_id = auth.uid()` → `cat_id` distinct

**구조 — 단일 목록 + 필터 칩.** 세로 3섹션·탭 3개는 폐기했다.

- **세 집합은 배타적이지 않다.** 나누면 같은 고양이가 두세 번 뜬다. **겹치는 집합에는 분할이 아니라 필터가 맞다**
- 칩 4개 — 전체 / 북마크 / 내가 등록 / 밥 준 적 있음. **단일 선택이다**
- 칩 스타일은 `.nearby-*` 재사용. 카드에 소속 배지. **검색·색·성별 필터는 넣지 않는다**

**북마크 저장 = 신규 테이블 `bookmarks`.**

- 컬럼 `user_id` · `cat_id` · `created_at`, PK `(user_id, cat_id)`

- soft-delete를 쓰지 않는다. 실제 DELETE다

## 6. 되돌린 것 (같은 실수 반복 방지)

- **좌표를 zone 참조로 저장하려던 코드 → 폐기.** 문서가 "50~100m 퍼징"으로만 적어놔서 재해석 여지가 생겼다
- **대학 이메일 도메인 검증 → 폐기**
- **"게스트에게 성별을 보여주는" 프로토타입 UI → 폐기**
- **"고양이 등록은 동아리원·관리자만" → 폐기.** 앱플로우와 로드맵이 정반대로 적혀 있던 항목
- **"Allow users without an email로 카카오 이메일 회피" → 폐기.** 코드로 우회되지 않았다. 비즈앱 전환으로 정면 해결
- **"문서에 적혀 있으니 구현도 그럴 것" → 폐기.** §2.3이 "두 뷰 모두 1시간 지연, 비협상"이었지만 실제 `cats_full`에는 없었다. **§2 항목이라도 코드로 확인하기 전까지는 "적혀 있다"일 뿐 "그렇다"가 아니다**
- **"노션과 로컬 md는 같은 문서다" → 폐기.** 가장 위험한 건 본문이 아니라 **차수 번호가 같은 값을 가리키지 않았다는 것**이다. **차수를 쓸 때는 날짜를 같이 적는다**
- **구버전 문서를 읽은 코드 감사 → 폐기.** 오탐 2건이 나왔고 그대로 따랐으면 확정 구조를 되돌릴 뻔했다. **감사·구현 전에 문서 버전부터 맞춘다**
- **"코드가 문서보다 뒤처져 있을 것" → 폐기. 어긋남은 양방향으로 생긴다**
- **"코드가 `verifyOtp`를 부르니 OTP 코드가 나가고 있을 것" → 폐기.** 외부 콘솔 설정이 어긋나면 코드·문서가 서로 맞아도 동작은 다르다
- **"사진 0장이면 색 기준 기본 일러스트" → 폐기. 확정 사항끼리도 충돌한다** — 새 항목을 §2에 넣을 때 기존 항목과의 충돌을 한 번 훑는다
- **"카카오 플랫폼에 도메인을 넣었으니 지도가 뜰 것" → 폐기.** 등록 지점이 두 곳이다. **외부 콘솔은 화면 하나가 설정 하나를 뜻하지 않는다**
- **"기본 SMTP로 소프트런치까지는 버틸 것" → 폐기.** 팀 멤버 외 주소로는 발송 자체를 거부한다. **개발자 본인 주소로만 테스트하면 이 종류의 제약은 끝까지 안 보인다**
- **"목격에는 사진을 받지 않는다" → 폐기.** **폐기 사유가 "결정이 틀려서"가 아니라 "전제가 만료돼서"인 첫 사례다.** §2 항목을 읽을 때 결론만 보지 말고 근거가 아직 살아 있는지 같이 본다
