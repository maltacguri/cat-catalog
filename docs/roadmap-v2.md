## 1. 정의와 원칙

### 한 줄 정의

한 대학 캠퍼스의 길고양이를 지도 기반으로 아카이빙하는 서비스.

"저 고양이 이름 뭐지?"라는 호기심으로 들어와서, "3시간 전 밥 먹음"을 보고 돌봄으로 이어지게 만든다.

### 차별점

급식 로그를 **개인 관리 기록이 아니라 낯선 사람에게 보내는 공개 신호**로 다룬다. 그리고 고정 급식소를 만들지 않는다.

### 원칙 5개 (기능 판단 기준)

1. **"찾아가게" 만들지 말고 "우연히 만났을 때 알아보게" 만든다.**
    - **금지** — 실시간 위치, 위치 기반 푸시/알림, 경로 안내, 실시간 거리 갱신, 특정 개체 추적
    - **허용** — 1시간 지연된 목격 기록을 조회·정렬·필터하는 정적 화면
    - 주변 고양이 보기(§2.7-5)는 허용 쪽이다. **지연을 우회하는 순간 금지 쪽으로 넘어간다**
2. **급식소는 만들지 않는다.** 고정 급식 장소 등록 기능 없음.
3. **급식 기록은 장소가 아니라 고양이 개체에 붙는다.**
4. **사진의 EXIF(GPS 포함)는 무조건 제거한다.**
5. **목격 좌표는 저장 시점에 50m 격자로 반올림한다.** 정밀 좌표는 DB에 존재하지 않는다.
6. **로그인만 하면 모두 고양이 등록할 수 있다.**

> 원칙 1은 2026-07-21에 문구를 좁혔다. 원래 "실시간 위치 알림·경로 안내 없음"이 §3-5(주변 고양이 보기)와 정면 충돌했다. 금지 대상은 **"지금 여기 있다"**이지 **"이 근처에 이런 애들이 산다"**가 아니다.
> 

> 원칙 5는 v1에서 "50~100m 퍼징"이라고만 적혀 있어서 구현이 두 번 뒤집혔다. **랜덤 오프셋이 아니라 결정적 라운딩이다.**
>

## 2. 확정 사항 — 다시 논의하지 않는다

### 2.1 인증 · 회원가입 (2026-07-19 확정)

**두 갈래를 모두 제공한다.**

| 방식 | 회원가입 | 이후 로그인 |
| --- | --- | --- |
| **이메일** | 가입 폼(이메일 + 비밀번호 + 비밀번호 확인) → 확인 메일 링크 클릭 | 이메일 + 비밀번호 |
| **카카오** | 카카오 인증 (`account_email` 동의항목 포함, §2.8-13) | 카카오 인증 (계속) |

**두 방식 공통:**

- 가입 시 앱 자체 프로필을 새로 만든다
- **집사 이름(닉네임)은 무작위로 자동 생성**한다
- 카카오의 닉네임·프로필 사진은 **저장하지도, 화면에 그리지도 않는다.** 카카오는 오직 인증 통과용
- **대학 이메일 도메인 제한 없음.** 학교별로 나누지 않고 위치 위주로 간다

**Supabase 매핑:**

- 이메일: `signUp({ email, password })` — 가입 폼에서 비밀번호까지 받는다 → 확인 메일 링크 클릭 → 이후 `signInWithPassword`
- 카카오: `signInWithOAuth({ provider: 'kakao' })` — Supabase 공식 지원
- 네이버는 채택하지 않는다 (공식 지원 없음, 우회 = 오버엔지니어링)

**메일 발송 인프라** *(2026-08-08 (27) 확정)*

- **커스텀 SMTP를 쓴다 — Resend + 자체 도메인 `gilnyangee.com`.** Supabase 기본 이메일 서비스는 프로젝트 전체 합산 시간당 2통이고, **프로젝트 팀 멤버가 아닌 주소로는 발송 자체를 거부한다.** 즉 기본 SMTP로는 실사용자가 한 명도 가입할 수 없다. 개발 중 본인 주소로만 테스트해서 이 사실이 드러나지 않았다
- **확장자는 `.com`이어야 한다.** `.xyz`·`.shop` 등 저가 확장자는 남용률이 높아 확인 메일이 스팸함으로 간다. 도메인을 사는 목적 자체가 무력해지므로 여기서 비용을 아끼지 않는다
- Resend도 **도메인 인증 전에는 계정 본인 주소로만 발송된다.** 커스텀 SMTP를 붙이려면 도메인 구매가 전제조건이다
- 커스텀 SMTP의 기본 한도 = 시간당 신규 사용자 30명. 429가 뜨면 Authentication → Rate Limits에서 숫자를 본다 — **2면 SMTP가 안 붙은 것이고, 30이면 붙은 것이다**
- **코드 변경 없음** — 전부 대시보드·DNS 설정이다
- **OTP 6자리 코드 방식은 2026-08-07 (24) 폐기.** `signInWithOtp` / `verifyOtp` / `updateUser({ password })` 3함수 삭제. 이메일 템플릿은 Supabase 기본값(`{{ .ConfirmationURL }}`)을 그대로 쓴다 — `{{ .Token }}`으로 바꾸지 않는다

**가입 폼은 3필드다 — 이메일 · 비밀번호 · 비밀번호 확인** *(2026-08-07 (24) 확정)*

- **아이디(username)는 만들지 않는다.** Supabase Auth가 username 로그인을 지원하지 않는다. 넣으려면 `profiles`에 username 저장 → 로그인 시 이메일 역조회 → `signInWithPassword` 2단계를 직접 짜야 한다. **스코프 초과**
- **이름(실명)은 받지 않는다.** 화면에 뜨는 건 무작위 닉네임이고, 실명은 §2.8-14의 "`profiles`에 민감한 컬럼을 넣지 않는다"에 걸린다
- **라벨을 placeholder가 아니라 실제 라벨로 노출한다.** 기존 로그인 폼이 placeholder만 써서 입력 후 무슨 칸인지 사라지는 문제가 있었다

**가입 대기와 완료 안내** *(2026-08-07 (24) 확정)*

- `signUp` 직후 session은 null이다. 원래 탭은 "메일 확인" 대기 화면에 머무른다
- `emailRedirectTo`는 `window.location.origin + '/?welcome=1'`. 링크가 열린 쪽에서 이 쿼리로 완료 오버레이를 띄운다. **라우트는 만들지 않는다** (§2.10 라우팅 표 불변)
- 링크는 메일 앱 인앱 브라우저에서 열릴 수 있다. **같은 브라우저면** supabase-js가 BroadcastChannel · localStorage로 탭 간 세션을 동기화하므로 원래 탭이 자동 로그인된다. **다른 브라우저면** 세션을 옮길 방법이 없다
- 그래서 대기 화면에 **"인증 완료했어요" 버튼**을 둔다(A안). 누르면 폼 state의 이메일 · 비밀번호로 `signInWithPassword`를 1회 시도한다. **자동 폴링은 하지 않는다** — 로그인 엔드포인트에 rate limit이 있고 포커스 시점 1회면 충분하다
- 비밀번호는 메모리(React state)에만 둔다. 대기 화면을 새로고침하면 무력화되지만, 그때는 로그인 폼에서 직접 로그인하면 되므로 막히지 않는다

**감수하는 것:**

- 이미 가입된 이메일로 다시 가입해도 "이미 가입됨"을 못 띄운다 — Confirm email이 켜져 있으면 Supabase가 계정 존재 여부를 숨기려고 가짜 user 객체를 반환한다
- 미확인 계정에 같은 이메일로 재가입하면 비밀번호가 갱신되지 않는다. 첫 번째 비밀번호가 남아 사용자는 두 번째 것으로 로그인을 시도하다 실패한다
- **선행 설정 3건은 코드가 아니라 Supabase 대시보드다** — ① Authentication → Providers → Email → `Confirm email` ON ② URL Configuration → Redirect URLs에 `http://localhost:5173/**`와 Vercel 주소 `/**` (쿼리가 붙으므로 와일드카드 필수) ③ 이메일 템플릿 기본값 유지

### 2.2 게스트(비로그인) 접근 범위 (2026-07-19 확정 · 2026-07-21 보강)

**게스트가 볼 수 있는 것은 딱 하나다. 지도에서 마커를 한 번 눌렀을 때 뜨는 카드.**

**카드에 들어가는 것 — 이게 전부:**

- 대표 사진 1장
- 이름
- 최근 밥 언제 먹었는지
- **자유 서술(`description`) 앞 2줄** — 2026-07-22 §2.11로 개정됨. 원래는 "특이사항(`traits`)"이었다

**성별은 카드에 없다.** 성별은 상세 프로필에만 나온다 (§2.7-1).

**게스트가 할 수 없는 것:**

- 상세 프로필 전체 (다른 사람이 올린 사진들 포함)
- 도감 리스트 · 검색 · 주변 고양이 보기
- 집사 프로필 · 마이캣
- 모든 쓰기 동작 (밥 주기, 목격 등록, 개체 등록)

> ⚠️ **컬럼 차단은 DB 뷰에서 한다** (§2.8-11). 게스트는 `cats_guest`를 읽으므로 성별·중성화는 애초에 내려오지 않는다. 다만 **화면 단위 제한(도감 리스트·검색·집사 프로필 차단)은 여전히 UI 레벨이다.** 컬럼 차단과 화면 차단을 구분해서 읽는다 *(2026-07-21 (4) 정정 — 원래 "전부 화면 레벨"로 적혀 있었다)*
> 

**하단 바는 게스트에게도 4탭 전부 보인다** *(2026-07-21 확정, 구 3-16)*

- 메인홈 외 3탭(주변 고양이 보기·마이캣·집사프로필)은 **숨기지 않고 잠금 상태로 노출**한다. 누르면 화면 전환 없이 로그인 유도를 띄우고 메인홈에 머문다
- 근거 — 앱플로우 §7이 게스트 제한을 "회원가입을 요구하는 요인"으로 규정했다. 숨기면 게스트는 앱에 더 있다는 걸 모른다
- 감수하는 것 — 게스트 체감이 "막힌 앱"이 된다
- 게스트가 잠긴 탭을 눌러도 **해당 화면의 데이터를 선제적으로 가져오지 않는다.** 잠금은 UI이고 실제 차단은 §2.8-11(뷰)·GRANT가 한다

> 구조로 보면 **플로팅 카드 = 게스트 / 상세 페이지 = 로그인 게이트.**
>

### 2.3 위치 저장 방식 (2026-07-17 확정 · 2026-07-19 재확인)

**write-time 라운딩, 격자 50m.**

```jsx
Math.round(v / 0.00045) * 0.00045
```

- 저장 **직전에** 반올림한다. 정밀 좌표는 DB에 들어간 적이 없다
- 유출돼도 나가는 건 격자까지
- 마커 UX·지도 바탕은 그대로. PostGIS 불필요
- **zones는 사용하지 않는다**
- **노출은 1시간 지연.** 프론트에서 숨기는 게 아니라 **DB가 안 준다.** `cats_guest` / `cats_full` 뷰가 집계 시점에 걸러서 `last_lat` / `last_lng`를 NULL로 내린다 (§2.8-11). **비협상** *(2026-07-21 (4) 정정 — 원래 "RLS"로 적혀 있었으나 실제 구현은 뷰다)*

`sightings` 컬럼:

| 컬럼 | 비고 |
| --- | --- |
| `lat` / `lng` | 50m 격자로 반올림된 값 |
| `cat_id` |  |
| `created_at` | 지연 계산 기준 |
| `deleted_at` | soft-delete |
| `reporter_id` | RLS의 "본인만 등록" 검사에 필요 |
| `photo_path` | 상세 페이지 갤러리에 필요 |

> 랜덤 오프셋이 아닌 이유: 랜덤은 같은 개체 기록이 쌓이면 평균으로 원본이 복원된다. 라운딩은 결정적이라 복원할 잔차가 없다.
> 

> 경도 `0.00045°`는 서울 위도에서 약 40m다. 격자가 50×40m 직사각형이 되는 건 감수한다.

### 2.4 사진 공개 범위 (2026-07-19 확정)

|  | 버킷 | 접근 |
| --- | --- | --- |
| **대표 사진 1장** | `cat-covers` (공개) | 누구나. 고정 CDN URL |
| **나머지 사진** | `cat-photos` (비공개) | 로그인 필요. 10분 만료 서명 URL |
- 업로드는 양쪽 다 로그인 필요
- **EXIF 제거를 통과한 파일만 업로드한다** (원칙 4)
- ⚠️ **공개 URL은 회수가 안 된다.** 대표 사진은 "인터넷에 공개한다"는 뜻으로 골라야 한다
- 사진이 1장뿐이면 자동으로 대표사진으로 등록한다

### 2.5 데이터 모델 — 아래 6 + deletion_requests + cat_reports = 실물 8테이블 (§2.16)

`campuses` · `cats` · `sightings` · `feedings` · `profiles` · `bookmarks`

> **zones는 제외한다.** 좌표가 `sightings`에 들어오면서 거리 계산으로 같은 일이 되므로 할 일이 없어졌다.
> 
- `campuses.status` = `hidden` / `open`
- **`campuses` 테이블과 `cats.campus_id`는 v1에서 미사용이다.** 스키마상 존재하지만 쓰지 않는다. 읽기는 지도 초기 중심·캠퍼스 이름 표시에만 남아 있다. 신규 등록 시 `cats.campus_id`는 NULL로 넣는다. `NOT NULL` 제약이 걸려 있으면 nullable로 바꾼다 *(2026-07-21 (3) 확정)*
- 삭제하지 않고 보류하는 이유: Postgres는 컬럼/테이블 추가·삭제 비용이 시점과 무관하므로 지금 지울 실익이 없다. **"나중에 쓰려고 남긴 것"이 아니라 "결정을 유보한 것"이다**
- `feedings`는 `cats`에 FK로 붙는다. 위치 컬럼 없음 (원칙 3). `kind` = 밥/간식/물 (§2.8-15)
- `profiles.role` = `user` / `club` / `admin` — §3-8 참고
- 실물 스키마·정책은 `docs/db-and-rls.md`에서 관리한다

### 2.6 v1 스코프

**만드는 것 (이것만):**

- 지도 + 마커 · 도감(개체 프로필) · 목격 등록 · 급식 원탭 기록 · 인증(§2.1)
- 주변 고양이 보기 (§2.7-5)
- 마이캣(북마크 · 등록 · 급식 기록) · 집사 프로필 · 급식 카운터 (§2.7-6, §2.12)
- 가입 퀴즈 · 서약서 (§2.7-7)

**안 하는 것:**

- 커뮤니티 / 게시판 · AI 고양이 자동 인식 · 실종 매칭 · 팔로우/좋아요/피드 · 앱스토어 배포

**확정된 권한 규칙:**

- 급식 기록은 지연하지 않는다 (위치 정보가 없고, "N시간째 기록 없음 → 내가 챙기자"가 핵심 루프라서)

### 2.9 2026-07-21 확정 — 조회 기준

**고양이 조회는 캠퍼스 단위가 아니라 좌표 bbox 기준으로 통일한다.**

```sql
WHERE lat BETWEEN ? AND ? AND lng BETWEEN ? AND ?
```

- 캠퍼스 단위 조회(`WHERE campus_id = ?`)는 어디에서도 쓰지 않는다
- bbox는 개념 정의, v1 실제 구현은 전체 조회
- 50m 격자로 반올림된 좌표(§2.3)라도 bbox 쿼리에는 지장이 없다
- 개체 수 수백 규모에서는 성능 차이가 없다. 전체 조회(`select * from cats`)로 두어도 v1에서는 무방하다
- **감수하는 것 — 도감이 "확정된 집합"이 아니게 된다.** "홍대 도감 47마리" 같은 고정 개수가 없고 항상 "지금 지도 범위에 보이는 N마리"다. 원칙 1("우연히 만났을 때 알아보게")상 도감은 컬렉션이 아니라 **식별 도구**이므로 일관된다
지도 초기 중심은 사용자 현재 위치다 (2026-08-09 (29) 개정). 최초 마운트 1회만 navigator.geolocation으로 잡아 중심을 옮긴다. 게스트에게도 적용한다
- 앱 진입 즉시 권한 팝업이 뜨는 것을 감수한다
폴백은 campuses 테이블 중심이다. 권한 거부·타임아웃·미지원 전부 폴백. campuses 읽기는 그대로 유지된다 (v1 미사용 원칙의 예외로 남아 있던 그 용도)
사용자 위치는 DB에 저장하지 않는다. 중심 계산에만 쓰고 버린다
원칙 1 경계
 — 자기 위치 표시는 허용, 고양이까지의 거리 실시간 표시·경로 안내는 금지. 이 둘이 붙는 순간 원칙 1 위반이다
감수하는 것 — 캠퍼스 밖에서 열면 마커 0개인 빈 지도가 뜬다. 소프트런치 테스터 대부분이 이 상태를 먼저 본다. B안(캠퍼스 반경 안에서만 이동)을 폐기하고 감수하기로 했다

- **8종 초안에서 바뀐 점** — 턱시도와 젖소를 "흑백" 하나로 합쳤다. 비율 판단(가슴 흰 점 vs 절반 흰색)이 사라지고, 부수 효과로 "배·발만 흰 고등어"가 젖소로 샐 길이 막혀 자동으로 고등어로 흘러간다. **흰색 섞임은 바탕색 기준**이라는 규칙이 목록 구조에 박혔다. 카오스는 삼색이에 병기, 회색 단색은 `other`로 흡수
- **CHECK 제약을 건다.** 값이 들어오는 경로가 폼·Supabase 대시보드·API 직접호출 3개인데 프론트 드롭다운은 첫 번째만 막는다. 목록 변경 시 `drop constraint` → `add constraint` 2줄이고, 슬러그 저장이라 **라벨 수정은 제약과 무관하다**
- **NOT NULL — 필수 항목이다** *(2026-07-23 (14) 개정. 원래는 nullable·선택이었다)*
- 기준 — **사진에서 관찰 가능한 것은 필수, 아닌 것은 "모름" 허용.** 대표 사진이 필수이므로 등록자는 사진을 보며 색을 고르는 상황이고, 7종은 육안으로 대부분 판별된다. **성별·중성화가 선택인 이유도 같은 기준이다** — 사진에 안 보인다
- **`default`는 걸지 않는다.** 기본값이 있으면 폼에서 안 골라도 값이 들어가 필수가 무력해진다. 폼에서 미선택 상태로 제출을 막는다
- **감수 — `other`가 도피처가 될 수 있다.** 애매한 개체가 전부 `other`로 몰리면 도감 검색이 다시 무력해진다. 실사용 후 `other` 비율을 한 번 본다
- **8종 초안 — 폐기됨 (2026-07-23).** 치즈 · 고등어 · 삼색 · 카오스 · 턱시도 · 검정 · 하양 · 젖소 → 위 7종으로 대체

**등록 확인 단계 (2026-07-22 확정)**

등록 폼보다 먼저 확인 한 단계를 둔다.

```
+ 버튼
 └ "주변에 등록된 다른 고양이들을 확인해보셨나요?"
    ├ 아니요, 확인해볼래요 → 도감
    └ 네, 확인했어요 → 등록 폼
```

- **강제가 아니라 선택이다.** 바로 등록하려는 사람을 막지 않는다
- 도감 화면에 **"새로 등록하기" 버튼**을 둔다. 확인 후 돌아올 경로가 없으면 질문을 또 보게 된다
- **데이터 0건일 때의 분기를 만들지 않는다.** 도감이 비어 있으면 빈 상태 화면(일러스트 + 안내문 한 줄)을 보여주면 된다
- ⚠️ **실제 데이터 수집 전에 Phase B 더미를 지운다.** 안 지우면 첫 등록부터 확인 화면에 더미가 뜬다

**v1에서 만들지 않는 것 (2026-07-22 확정)**

- **위치·색 기준 자동 매칭** — 앱플로우 §4의 "이 고양이가 맞습니까?" 후보 제시. 시스템이 후보를 추리는 건 §2.6이 v2로 미룬 AI 개체인식과 같은 성격이다. **사람이 눈으로 확인하는 단계만 v1에 넣는다**
- **주소검색** — 앱플로우 §4의 "주소검색 / 드래그". 캠퍼스 1개라 지도 드래그로 충분하고, 주소검색은 카카오 로컬 API를 따로 붙여야 해서 스코프 대비 이득이 적다

### 2.12 2026-08-08 확정 — 마이캣 화면

**마이캣은 "내가 소유한 고양이"가 아니라 나와 엮인 개체를 모으는 화면이다.** 근거 세 가지를 모은다.

- **북마크함** — `bookmarks` where `user_id = auth.uid()`
- **내가 등록함** — `cats_full.created_by = auth.uid()`
- **밥 준 적 있음** — `feedings.giver_id = auth.uid()` → `cat_id` distinct

**구조 — 단일 목록 + 필터 칩.** 세로 3섹션·탭 3개는 폐기했다.

- **세 집합은 배타적이지 않다.** 등록한 고양이는 대개 밥도 주고, 북마크도 급식과 겹친다. 나누면 같은 고양이가 화면에 두세 번 뜬다. **겹치는 집합에는 분할이 아니라 필터가 맞다**
- 칩 4개 — 전체 / 북마크 / 내가 등록 / 밥 준 적 있음. **단일 선택이다** (NearbyPage의 색·성별 다중 칩과 다르다 — 여긴 교집합이 의미 없다)
- 칩 스타일은 NearbyPage의 `.nearby-*`를 재사용한다. 새 UI 패턴을 만들지 않는다
- 카드에 소속 배지를 단다. 중복이면 여러 개
- **검색·색·성별 필터는 넣지 않는다.** 내 기록이라 훑으면 끝난다
- 카드 탭 → `openDetail(catId)` 오버레이 (§2.10, (25)차 Context)
- 빈 상태 문구는 1개. 칩별로 나누지 않는다

**정렬 — "나와 마지막으로 엮인 시각" 내림차순.**

- 내 마지막 급식 `fed_at` · 등록 `created_at` · 북마크 `created_at` 중 **가장 최근 값**
- 그 고양이가 마지막으로 밥 먹은 시각(`cats_full.last_fed_at`)이 **아니다.** 남이 준 기록까지 섞이면 이 화면이 내 기록이 아니게 된다. "오래 굶은 개체 띄우기"는 지도·도감이 하는 일이다

**북마크 저장 = 신규 테이블 `bookmarks` (§3-17 종결).** §2.5가 5테이블 → **6테이블**이 된다.

- 컬럼 `user_id` uuid · `cat_id` uuid · `created_at` timestamptz, PK `(user_id, cat_id)`
- 토글이 INSERT / DELETE 한 줄이라 원자적이다. **`profiles` 배열 안은 폐기** — 토글마다 read-modify-write라 동시 클릭 시 조용히 유실되고, 북마크 시각을 못 남겨 정렬 키가 사라진다
- **§2.5의 테이블 개수는 원칙이 아니다.** `zones`를 뺀 결과를 적어둔 것이지 상한이 아니다
- RLS 3정책 — SELECT / INSERT / DELETE, 전부 `user_id = auth.uid()`. **UPDATE 정책은 만들지 않는다** (수정할 컬럼이 없다)
- GRANT는 `authenticated`의 SELECT/INSERT/DELETE 3개만. `anon`은 전량 회수했다 (§2.8-11 — 방어선은 GRANT다). **신규 테이블은 기본으로 `anon`에 7개 권한이 전부 붙어 나온다** — 만들 때마다 회수하고 확인한다
- soft-delete를 쓰지 않는다. 실제 DELETE다
- 진입점은 `CatDetailPage` 히어로 우측 상단(에어비앤비 하트 위치). 게스트는 `openAuth`

### 2.13 2026-08-10 확정 — 목격 사진 첨부

**"여기서 봤어요"에서 사진을 1장 받는다.** (23)차의 "사진은 받지 않는다"를 뒤집는다.

- **선택이다.** 사진 없이도 목격 등록은 지금처럼 그대로 된다
- 저장 위치는 `sightings.photo_path`. 버킷은 `cat-photos`(비공개, §2.4). **목격 1건당 1장** — 컬럼이 단수다
- 상세 페이지 "다른 사진들" 갤러리가 이 값을 읽는다. **갤러리는 원래부터 `sightings`에서 나오고 있었다** — 읽는 쪽은 이미 완성돼 있었고 `addSighting`이 `photo_path: null`을 하드코딩하고 있던 것뿐이다
- **뒤집는 근거** — (23)차의 이유는 "붙이면 업로드 UI가 통째로 딸려온다"였다. Phase D(업로드·EXIF 제거·HEIC 변환·썸네일)가 끝나면서 그 이유가 사라졌다

**업로드는 제출 시점이다.** 파일을 고를 때는 미리보기만 만든다.

- `storage.objects`에 UPDATE/DELETE 정책이 없어 한 번 올라간 파일은 **아무도 못 지운다.** 고르자마자 올리면 취소한 사용자마다 고아 파일이 남는다
- 대가 — `uploadSightingPhoto`가 내부에서 변환을 다시 돌려 미리보기와 중복 작업이 생긴다. `api/photos.js` 시그니처를 안 건드리는 쪽이 싸다고 판단했다

**`sightings` SELECT 정책에 본인 행 예외를 넣었다.**

```sql
(deleted_at is null and (created_at <= now() - sighting_delay() or reporter_id = auth.uid())) or is_staff()
```

- **이유** — 갤러리가 `sightings`에서 나오므로 1시간 지연을 그대로 상속한다. 그러면 방금 올린 내 사진이 나에게도 1시간 동안 안 보인다. 좌표는 눈에 안 보이는 정보라 (23)차에서 문구로 감당됐지만, **사진은 내가 방금 만든 눈에 보이는 산출물이라 부재를 업로드 실패로 읽는다.** 같은 사진을 여러 번 올려 1시간 뒤 중복이 쌓인다
- **원칙 1과 충돌하지 않는다** — 여는 범위가 `reporter_id = auth.uid()`, 내가 올린 행뿐이다. 남에게는 여전히 1시간이다
- ⚠️ **지도 좌표는 영향받지 않는다.** `cats_full`·`cats_guest`는 `security_invoker`가 꺼져 있어(`reloptions` = null, 2026-08-10 재확인) 기저 테이블 RLS를 타지 않고 뷰 자체 `sighting_delay()` 필터로 지연을 건다. **이 조건이 깨지면 이 정책 변경은 즉시 롤백 대상이다**
- `deleted_at is null`을 본인 행에도 걸었다. 안 걸면 staff가 내린 사진이 올린 사람에게는 계속 보인다
- **`.select()` read-back은 여전히 붙이지 않는다.** (23)차 결정 유지 — INSERT 성공 여부만 본다

**갤러리는 썸네일을 먼저 로드한다.** `_thumb.jpg` 경로 파생, 실패 시 원본 폴백.

- `uploadSightingPhoto`가 원본과 썸네일을 `Promise.all`로 같이 올리므로 한쪽만 남는 상태가 없다. **`thumb_path` 컬럼을 추가하지 않은 이유다**
- 원본 1600px 8장이면 3~4MB, 썸네일 480px 8장이면 약 400KB

**v1에서 만들지 않는 것**

- **인당 사진 개수 제한** — 갤러리가 최근 8장 컷(`.limit(8)`)이라 한 사람이 여러 번 올리면 등록자 사진이 밀린다. **감수한다**
- 갤러리 사진 삭제·신고·대표사진 승격 — Phase F

### 2.16 2026-08-12 확정 — 고양이 민원 창구

**진입점 — MePage 「안내」 하위.** 사용자는 요청만 넣고, 실제 삭제·상태 변경은
개발자가 Supabase 대시보드에서 한다. **인앱 관리 화면을 만들지 않는다.**
- **§3-9 종결 — 민원 담당자는 개발자 1명이다.**
- **§3-8(role 모델)을 닫지 않아도 된다** — `is_staff()`를 쓰는 화면이 없다.
  처리는 `postgres` 권한(대시보드)이 한다.

**신규 테이블 `cat_reports`.** `deletion_requests`(계정·개인정보 삭제)와 분리한다.
- **화면은 하나, 저장은 둘.** 아코디언 하나만 보이고 분기는 제출 시점에 한다.

| 컬럼 | 비고 |
|---|---|
| `id` / `created_at` | DB 기본값 |
| `user_id` | → `profiles(id)` ON DELETE CASCADE |
| `cat_id` | NULL 허용. → `cats(id)` ON DELETE SET NULL |
| `kind` | `profile` / `photo` / `other` 3종. CHECK |
| `note` | 사용자 서술. 도감번호·이름을 여기 적는다 |
| `status` | `pending` / `resolved` / `rejected`. default `pending`. CHECK |
| `admin_note` | 거절 시에만 사유. 처리되면 `status`만 바꾼다 |

**고양이 특정은 `note`로 한다.** 선택 목록 UI를 만들지 않는다.
**RLS 2정책** — SELECT / INSERT, 둘 다 `user_id = auth.uid()`. UPDATE 정책 없음.
**GRANT** — `authenticated` SELECT/INSERT 2개. `anon` 0행 (2026-08-12 검증 완료).

**`cats_full`에 `WHERE c.status = 'active'` 필터를 추가했다.**
- 새 상태를 만든 게 아니라 비대칭을 맞춘 것이다. `cats_guest`엔 원래 있었다.
- 없으면 확실한 처리 수단이 실제 DELETE뿐이고, DELETE는 되돌릴 수 없다.
- ⚠️ 확인 필요 — MyCatPage. 내가 등록·급식한 고양이가 `hidden` 되면 목록에서 사라진다.

**무지개다리는 v1에 넣지 않는다.** `cats.status`의 `gone`은 의미가 정의돼 있지 않고,
추모는 "보여야 하는" 상태라 게스트 뷰의 `active` 필터와 충돌한다. 접수는 `other`로 받는다.

**⚠️ 이번에 드러난 실물 3건 (문서에 없던 것)**
1. `cats.status` = `active` / `hidden` / `gone`, CHECK 존재. §2.11은 "DB 기본값"이라고만 적었다
2. `deletion_requests` 테이블이 §2·§5에 기록 없이 존재한다 (계정 삭제 전용)
3. `is_staff()`에 이은 선반입 사례 — "코드가 문서보다 앞선다"의 DB판

**⚠️ 자식 3테이블이 전부 CASCADE다** — sightings / feedings / bookmarks → cats(id).
`cats` 1행 삭제 시 목격·급식·북마크가 동반 삭제되고 복구 불가다. Storage 파일은 남는다.
**따라서 실제 DELETE는 최후 수단이다. 통상 처리는 `status = 'hidden'`.**
⚠️ `cats.campus_id` → `campuses`도 CASCADE다. 캠퍼스 행 삭제 시 그 고양이가 전멸한다.

### 되돌린 것 (같은 실수 반복 방지)

- **좌표를 zone 참조로 저장하려던 코드 → 폐기.** 문서가 "50~100m 퍼징"으로만 적어놔서 재해석 여지가 생겼다
- **대학 이메일 도메인 검증 → 폐기.** 7/18 결정으로 이미 빠진 상태
- **"게스트에게 성별을 보여주는" 프로토타입 UI → 폐기.** §2.2 확정과 어긋난다
- **"고양이 등록은 동아리원·관리자만" → 폐기.** 앱플로우와 로드맵이 정반대로 적혀 있던 항목. §2.8-12로 전체 개방 확정
- **"Allow users without an email로 카카오 이메일 회피" → 폐기.** 실제로는 카카오 쪽에서 이메일을 요구했고 코드로 우회되지 않았다. 비즈앱 전환으로 정면 해결
- **"문서에 적혀 있으니 구현도 그럴 것" → 폐기.** §2.3이 "두 뷰 모두 1시간 지연, 비협상"으로 적혀 있었지만 실제 `cats_full`에는 없었다(2026-07-21 (6)). **§2 항목이라도 코드로 확인하기 전까지는 "적혀 있다"일 뿐 "그렇다"가 아니다**
- **구버전 문서를 읽은 코드 감사 → 폐기.** 2026-07-22 감사에서 Claude Code가 (2) 시점 `roadmap-v2.md`를 읽고 §2.8-11(뷰 방식)과 §2.8-14(`profiles`)를 "위반"으로 판정했다. **둘 다 오탐이었고, 그대로 따랐으면 (4)·(6)에서 확정한 구조를 되돌릴 뻔했다.** 감사·구현을 시키기 전에 **문서 버전부터 맞춘다** — 확인은 §5 변경 이력 마지막 행 한 줄이면 된다
- **"코드가 문서보다 뒤처져 있을 것" → 폐기.** 이번엔 반대였다. 체크리스트가 `[ ]`인 항목이 이미 구현돼 있었다. **어긋남은 양방향으로 생긴다**
- **"코드가 `verifyOtp`를 부르니 OTP 코드가 나가고 있을 것" → 폐기.** 코드도 문서도 OTP로 일치했지만 Supabase 이메일 템플릿이 기본값(링크)이라 6자리 코드가 나간 적이 없었다(2026-08-07 (24)). **코드와 문서가 서로 맞아도 외부 콘솔 설정이 어긋나면 동작은 다르다.** 검증 대상은 코드 · DB · 문서 셋이 아니라 넷이다
- **"사진 0장이면 색 기준 기본 일러스트" → 폐기.** 등록 폼에서 대표 사진을 필수로 확정하면서 도달할 수 없는 규칙이 됐다(2026-07-23). **확정 사항끼리도 충돌한다** — §2.11(사진 필수)과 §2.7-8(사진 0장 처리)이 같은 §2 안에서 공존했다. 새 항목을 §2에 넣을 때 기존 항목과의 충돌을 한 번 훑는다
- **"카카오 플랫폼에 도메인을 넣었으니 지도가 뜰 것" → 폐기.** 카카오는 도메인 등록 지점이 **두 곳**이다 — 플랫폼(Web)의 '사이트 도메인'과 JavaScript 키 설정 안의 '**SDK 도메인 설정**'. 뒤쪽을 비워두면 지도가 401로 막히는데, 앞쪽 목록에는 도메인이 멀쩡히 등록돼 있어 **"등록했는데 안 된다"로 보인다**(2026-08-08 (27)). (24)차 "검증 대상은 넷이다"의 연장선 — **외부 콘솔은 화면 하나가 설정 하나를 뜻하지 않는다**
- **"기본 SMTP로 소프트런치까지는 버틸 것" → 폐기.** Supabase 기본 이메일은 팀 멤버 외 주소로 **발송 자체를 거부**한다. 친구 테스트조차 불가능하므로 한도 문제가 아니었다(2026-08-08 (27)). **개발자 본인 주소로만 테스트하면 이 종류의 제약은 끝까지 안 보인다**
- **"목격에는 사진을 받지 않는다" → 폐기.** (23)차가 "붙이면 업로드 UI가 통째로 딸려온다"를 이유로 확정했는데, Phase D가 끝나면서 그 이유 자체가 사라졌다(2026-08-10 (30)). **폐기 사유가 "결정이 틀려서"가 아니라 "전제가 만료돼서"인 첫 사례다.** §2 항목을 읽을 때 결론만 보지 말고 근거가 아직 살아 있는지 같이 본다
